# Coach final-review traps

The authoritative workflow and programming rules are in [SKILL.md](../SKILL.md); do not maintain a second copy here. Before delivery, confirm person/path selection, the recovery gate and explicit overrides, saved-assessment-before-plan checkpoint, block continuity, `next_dose`, split and main-pattern coverage, core/arm/muscle floors and placement, deload handling, and strength-only bullet formatting. Run `check_plan.py` until blocking errors are fixed; correct advisory dose, pattern and cardio warnings unless the opener states a deliberate exception. Relay remaining warnings.

Checks do not choose the split, respond to stalls, or prescribe the cadence deload for the coach. Follow the skill rules even when a validator would accept the plan. The traps below concern interpretation rather than a duplicate programming specification.

| Failure mode | What goes wrong | Correct behavior |
|---|---|---|
| Re-summing volume that the script already has | Manually adding `rows` for a muscle and re-applying the fractional model | Read `weekly_volume_per_muscle.current[muscle]` directly. The script has already excluded warmups and applied the 1.0/0.5 rule. |
| Ignoring `unknown_exercises` | Volume numbers look low because several logged exercises don't match the database and contribute zero | Surface the list in **Missing from your tracking**. Typos/rename-drift silently under-count volume until fixed. |
| Warmup sets counted as working volume | `Jumping Jacks 1×50` treated as a hard set | Warmup exercises and sets with `(warmup)` in Notes are excluded from hard-set counts. |
| Generic advice when data is thin | "You should probably add more back work" without numbers | State exactly what you can see ("2 sessions, 4 back sets") and what you can't conclude. |
| Progression call on insufficient data | "Bench press is stalling" from 2 data points | Need 3+ sessions over 2+ weeks. Below that: "not enough data to call a trend." |
| Inventing numbers not in the tracker | Estimating weights/reps the user didn't log | Only use data present. Empty field = unknown. |
| Missing data from casing mismatch | Searching for "Leg Extension" misses rows logged as "Leg extension" | Compare case-insensitively. |
| Inventing recovery trends on <4 readings | "VO2max improving" called from 2 data points | The `_trend_per_4w` keys are null until ≥4 entries spanning 21+ days. Drop the trend chunk; print the average alone. |
| Treating Apple `Walking` workouts as training | Counts a 5-min stroll as a session | The importer classifies incidental walks through the typed `Incidental` field, not boilerplate Notes. `monthly_sessions` already excludes them; don't re-add them when reading the sheet directly. |
| Treating source-limited HRV as "not enough data yet" | Implies the user just needs to log more, but the source can't provide HRV at all | Read `capabilities.hrv`. If False, omit the metric (and its sections) entirely. Distinct from "trend is null because <4 readings collected so far". |
| Listing structurally-unsupported metrics in **Missing from your tracking** | User sees a fake to-do list of things to "track" that the data source can't supply | The section is for *fixable* gaps (typos in `unknown_exercises`, dropped exercises, manual notes). Anything False in `capabilities` belongs in source docs, not the user-facing report. |
| Treating auto-cardio rows as duplicates of manually-logged runs | Both /log and the importer write the same run; coach can't tell them apart | Auto-cardio dedupe runs in the importer by (date, exercise, duration ±1 min). Manual entries always win. If you see two rows for the same run on the same date, flag it — the dedupe missed something. |
| Treating an annotated outlier as a typo | The user wrote in Notes that the row reflects equipment / gym / context change; coach calls it "almost certainly a typo" anyway | Read `progression_summary[exercise].last_notes` (or full Notes via `--include-rows`). If a note exists, treat the row as user-acknowledged context, not as an error. Acknowledge the context in the bullet rather than calling it a logging error. |
| Skipping `swim_trajectory_callout` when `swim_summary` is present | The assessment lists structured 14d swim trends without coach commentary: the user reads numbers without judgment | Gate on `swim_summary` key presence. When present, author `cards.swim_trajectory_callout` per the card list in SKILL.md (verdict + 1 driver + 1 actionable focus). |
| Skipping `nutrition_phase_callout` when `nutrition_phase` is present | The assessment lists the bulk/cut phase without a judgment; the binding `coach_action_hint` token reads as ungrounded | Gate on `nutrition_phase` key presence. When present, author `cards.nutrition_phase_callout` per the card list in SKILL.md. For `current.phase_type == "bulk"`, read `references/bulking-science.md` first. |
| Treating a context-change row as a real strength regression | Cable Lateral Raise drops from 15kg to 7kg after a gym change; coach flags the lift as "going backwards" with a -32kg/4w slope, even though the user's Notes say "new gym, different cable weights" | Read `estimated_1rm[exercise].context_change_excluded` and `progression_summary[exercise].last_notes`. When `context_change_excluded ≥ 1`, write "Slope reset by gym/equipment change; trend resumes once 3+ sessions logged on the new equipment" instead of calling stall or regression. |
| Reporting an unresolved bodyweight trend as a direction | "Down 0.37 kg/wk" over a stretch whose honest fit was +0.07 ± 0.25; the coach reported leaning out across a stretch the user actually gained weight over | Read `bodyweight_trend.state` first. `unresolved` is an answer: say the direction is not resolved and give the reason. Never quote `point_kg_per_week` — or waist's `point_cm_per_4w` — as if it were the rate. Both sit beside `state` in their block and neither is gated on anything: the state check is the reader's job. |
| Reading body composition off the scale when waist is empty | "Up 1.2kg — the bulk is working" with no `waist_latest` on file. Bodyweight alone cannot separate recomposition from fat gain, so the claim is a coin flip dressed as a finding. | Waist is the leanness channel. With `waist_trend_cm_per_4w` resolved, read the two together. With one reading, call it a baseline and claim no direction. With `waist_latest` null, say the channel is empty out loud instead of omitting it — a silent omission reads as "nothing to report". |
| Trusting recovery `confidence: high` on under-sampled signals | A high-weight signal with `n_recent: 1` (one HR-Recovery reading) inflates confidence to "high" even though the score is hanging on one data point | Confidence is gated on per-signal sample sufficiency in `health_recovery.py`. When the JSON shows `confidence: medium` or `low` after a thin recent week, soften any rule that relies on the score band — and cite the under-sampled driver by name. |
