# Coach — Common Mistakes

Catalog of known failure modes with the correct behavior for each. Read this before finalizing a plan or dashboard. Grouped loosely: planning/programming first, then data-reading, then dashboard-gating.

`check_plan.py` blocks (exit 2) on: exercise names outside the catalog, the workout copy rules (em dashes, core and arm placement), the core spec, the per-muscle weekly floors, and `coach_reads.json` or opener numbers that contradict the payload. Set grammar is not checked directly: a malformed set (`Plank: 45s hold`) just counts as one set and can trip the core spec. The set budget and block rotation only warn, and so do three more: a written dose that differs from `next_dose`, a week missing one of the four main patterns, and a cardio section. Those warnings are not a licence: getting it right is still the coach's job, and a warning means fix the plan before saving. **No check covers** the stall response, the split choice or the deload session: the coach has to follow those unprompted. Where a row states a number, the number lives in `lib/constants.py` (`CORE_WEEK_SPEC`, `RP_DIRECT_SET_LANDMARKS`, `VOLUME_LANDMARKS`); this table names the failure mode and the judgement.

| Failure mode | What goes wrong | Correct behavior |
|---|---|---|
| Re-summing volume that the script already has | Manually adding `rows` for a muscle and re-applying the fractional model | Read `weekly_volume_per_muscle.current[muscle]` directly. The script has already excluded warmups and applied the 1.0/0.5 rule. |
| Ignoring `unknown_exercises` | Volume numbers look low because several logged exercises don't match the database and contribute zero | Surface the list in **Missing from your tracking**. Typos/rename-drift silently under-count volume until fixed. |
| Warmup sets counted as working volume | `Jumping Jacks 1×50` treated as a hard set | Warmup exercises and sets with `(warmup)` in Notes are excluded from hard-set counts. |
| Generic advice when data is thin | "You should probably add more back work" without numbers | State exactly what you can see ("2 sessions, 4 back sets") and what you can't conclude. |
| Progression call on insufficient data | "Bench press is stalling" from 2 data points | Need 3+ sessions over 2+ weeks. Below that: "not enough data to call a trend." |
| Inventing numbers not in the tracker | Estimating weights/reps the user didn't log | Only use data present. Empty field = unknown. |
| Choosing a weight instead of copying `next_dose` | A bench sits at 44 kg for 12 weeks while the range climbs 8-10, 10-12, 12-14, because the coach held the load on a recovery band and widened the range. Or a cable is bumped to a number nobody computed. | Write `next_dose.exercises[].load_kg` and `rep_range` exactly. Weight goes up only when `action` is `add_load` (every working set hit the top of the range). Never widen a range, re-round or convert a load. Compounds top out at 12 reps and isolation at 20; past that the lift is owed weight. |
| Scattering equipment | Cable exercises in positions 2, 5, 9 of the session | Batch by equipment within the isolation/accessory block. Never break compound order. |
| Neglecting core | Core absent, or present only as the last bullet, or prescribed as a movement the log shows is never performed | Dose and weekly distribution come from `core_week_spec` and block the render, and so does placement — core as a workout's **last bullet** is a blocking error, not a style note. Put it inside the isolation block as straight sets, never before a compound. The judgement call is selection against `adherence.benched` / `never_performed`. See §24. |
| Satisfying the core spec degenerately | The same loadable flexion machine repeated across every session: quantity target met, one pattern category, zero anti-rotation, zero carry. The measured 6-month outcome was 94% flexion. | Slot A is loaded flexion, slot B rotates a non-flexion category by block (§24.3). Distinct exercises, pattern categories and per-exercise frequency are all blocking axes; a plan that clears sets-per-session and fails those does not ship. |
| Running the same exercises every session | Weekly volume looks fine but regions of each muscle go chronically under-stimulated (§17) | The week's selection must cover different regions per target muscle. Use the `exercises-database.md` tags to pick the second variant. |
| Over-rotating variants every block | No single exercise repeats often enough to read a progression trend | Keep at least one anchor per muscle stable. Rotate 1-2 secondary variants per mesocycle, not the main lifts. |
| Ignoring the deload clock | 7+ weeks of continuous blocks because no one flagged it | Read `block.deload_prescribed`, `block.weeks_since_deload` and `block.deload_cadence_due`; do not compute weeks yourself. When `deload_prescribed` is true, prescribe ONE deload session, the first lower-body session of the week (not a full-block halving; core keeps its dose), and disclose it in the opener. A full-block deload is for gate Tier B / `load_policy` `reduce` or an explicit user request. |
| Defaulting to PPL / keeping a low-frequency split | Push/Pull/Legs at 3-4 sessions trains each muscle ~1x/week, so volume sits below MEV | Pick the split from `strength_sessions_per_week` (§14): 2-3/wk → Full Body, 4/wk → Upper/Lower. Each muscle ~2x/week. |
| Muscles fed only by synergy | Biceps and triceps get no direct isolation because rows and presses "cover" them in the volume model; a shoulder press disappears when the split changes | Every muscle in `muscle_floors` has a weekly floor in DIRECT sets (primary-muscle exercises only; synergist credit never counts), blocking in `check_plan`. `arm_week_spec` adds the distinct-exercise axis. A biceps or triceps exercise as a workout's **last bullet** blocks too: arms sit inside the isolation block and something that is neither arms nor core closes the session. |
| A main pattern missing from the week | The split moves from Push/Pull/Legs to Upper/Lower and the overhead press silently drops out for three months | Every week needs a horizontal push, a vertical push, a horizontal pull and a vertical pull. `rotation_candidates` always offers a main pattern with no working set in the last 56 days, with a derived load. `check_plan` warns when one is missing (advisory); fix the plan before saving. |
| Prescribing normal volume after a long break | User took 10 days off, coach plans a full 4-set compound session | Compute days-since-last-session from `monthly_sessions[-1].date`. >5 and no deload → re-entry session with reduced sets and more RIR on the first day back (§7). |
| Prescribing cardio in the plan | A `## Cardio N` section, a Zone 2 or interval session, or a cardio instruction in the plan intro, typically when the person is behind the §10 target | The plan is strength only, always. Cardio data feeds the analysis (recovery, training load, fatigue, the cardio and behavioural cards in `coach_reads.json`) and is never prescribed. A §10 shortfall is stated on the card, not fixed in the plan. |
| Static plan with no mesocycle context | Weights and reps with no indication of block position | Tell the user where they are in the mesocycle and what this week targets (§15). |
| Missing data from casing mismatch | Searching for "Leg Extension" misses rows logged as "Leg extension" | Compare case-insensitively. |
| Writing the report or plan inline in chat | Conversation gets flooded; plan is hard to find later | The assessment and plan go to `plans/<Person>/<date>-coach_reads.json` and `plans/<Person>/<date>-workout.md`, plus `plans/<Person>/<date>-assessment.html` only when the user asked for the report. Chat gets one verdict line, the file pointers, and any `check_plan.py` warnings. |
| Rendering the HTML report when nobody asked for it | An `assessment.html` written on a plain `/coach` run | The report is opt-in. Render it only when the `/coach` message asks for a report, dashboard or assessment. `check_plan.py` runs the same checks without it. |
| Skipping the checks because there is no report | Plan written, no script run, so the core and arm floors, set budget and opener cross-check never ran | `check_plan.py` runs on every `/coach` and must exit 0 before the plan counts as done. The report renderer is not the check. |
| Deciding a Tier A or B day alone | A rest day, Zone 2 day or deload week written straight from the gate's call | Stop after `read_tracker` and ask: rest day, lighter strength, or normal strength via `--override-gate`. See `references/substitute-protocols.md`. Tier C stays automatic. |
| Writing one person's plan over another | A dated file in the wrong `plans/<Person>/` folder, or the wrong person's data rendered into the right person's HTML | Resolve the person first; pass `--person <Name>` to `read_tracker.py`; use `person_paths.plans_dir(person)` to build the output path. Never hand-assemble a path. |
| Writing to the old root-level `./workout_plan - <Person>.md` | The lean / HTML split is bypassed; the user opens the wrong file | The old root-level file is frozen history. All new output lands in `plans/<Person>/`. Use the path resolvers in `shared/person_paths.py`. |
| Adding a rationale table under each workout's bullet list | Recreates the old `| # | Exercise | Sets × Reps | Notes |` table that the user explicitly removed; clutters the gym-floor view | The workout markdown is bullets only — no markdown tables. Per-exercise rationale lives in the dashboard's coach's-read lines, not in the workout file. |
| Writing a sub-bullet note on every exercise | Bullet list balloons; the few important notes get drowned out | Sub-bullet notes (`  — …`) are sparse by design (0-2 per workout, 3+ is a red flag). Use them only for: form cue that matters today, safety/injury awareness, or a one-time deviation from autopilot. Strip comparative history ("last time X"), restated rationale, and generic exhortation. |
| Rationale creep in sub-bullet notes | `— last session 50kg × 6, time to push to 52.5` ends up under every other exercise | The bullet itself prescribes the weight. The note explains nothing about the prescription — it's reserved for form, safety, or a single deviation. If the prescription needs justification, put it on the dashboard's strength-progression card's coach's read. |
| Reintroducing a `## Why this plan` block in the workout markdown | Adds 3-4 sentences of rationale to the file the user trains from | The three-signal rationale lives in the dashboard's per-card coach's-read lines now. The workout markdown ends after the last strength workout. |
| Surfacing rationale that mentions "last time" | "Stuck at 40kg — push for 8 reps before bumping" survives into the workout md | Comparative history is banned from the workout markdown. It belonged to the deleted table. Trust the bullets. |
| Dashboard depends on a network resource | `<script src="https://…">`, web font, CDN CSS, remote image | Self-contained file: inline CSS, inline SVG, inline JS only. Verify by opening with Wi-Fi off — must render identically. |
| Dashboard surfaces gamification | "5-week streak!", badges, points, consistency score | The user explicitly rejected gamification. Stay with neutral health + fitness signals. |
| Hardcoding the training-load chart to 60 days (or another non-90 window) | CTL is a 42-day EWMA, so a 60-day window crops out half the mesocycle context | Use a 90-day window for the CTL/ATL/TSB curve. Don't accept smaller windows for "cleaner-looking" charts — the curve becomes uninformative. |
| Ignoring cold-air outdoor temperature when present | `cold_air -2°C × 5min` rendered identically to `cold_air × 5min`; user can't tell a real dose from a habit | Surface `thermal_summary.cold.recent_sessions[*].cold_temp_c` on the Recovery practices card. When `dose_hint == "amber"` (cold_air ≥ 18°C), tag it. Coach's read names a -2°C outdoor session as a real dose. |
| Partial file writes | Streaming sections and forgetting to complete | Build the whole file in memory, then write once. |
| Inventing recovery trends on <4 readings | "VO2max improving" called from 2 data points | The `_trend_per_4w` keys are null until ≥4 entries spanning 21+ days. Drop the trend chunk; print the average alone. |
| Reacting to one bad night | One bad night triggers a deload | The `recovery.score` already aggregates 7-day resting HR / sleep / HR Recovery against baselines. Trust the score; don't react to one bad night. For multi-day persistence checks, walk `health_metrics_weekly` (or pass `--include-daily-health` only when the rolling-window inspection genuinely matters). |
| Treating Apple `Walking` workouts as training | Counts a 5-min stroll as a session | The importer flags walks under 15 min as `incidental walk` in Notes. `monthly_sessions` already excludes them; don't re-add them when reading the sheet directly. |
| Adding sets to a muscle whose session HR is creeping up | User over-reaches | Per-muscle call: `hr_at_volume_divergence[muscle].hint`; absolute HR: `monthly_sessions[*].avg_hr`. A flagged muscle gets no added sets this block (loads still follow `next_dose`). |
| Treating source-limited HRV as "not enough data yet" | Implies the user just needs to log more, but the source can't provide HRV at all | Read `capabilities.hrv`. If False, omit the metric (and its sections) entirely. Distinct from "trend is null because <4 readings collected so far". |
| Listing structurally-unsupported metrics in **Missing from your tracking** | User sees a fake to-do list of things to "track" that the data source can't supply | The section is for *fixable* gaps (typos in `unknown_exercises`, dropped exercises, manual notes). Anything False in `capabilities` belongs in source docs, not the user-facing report. |
| Treating auto-cardio rows as duplicates of manually-logged runs | Both /log and the importer write the same run; coach can't tell them apart | Auto-cardio dedupe runs in the importer by (date, exercise, duration ±1 min). Manual entries always win. If you see two rows for the same run on the same date, flag it — the dedupe missed something. |
| Treating an annotated outlier as a typo | The user wrote in Notes that the row reflects equipment / gym / context change; coach calls it "almost certainly a typo" anyway | Read `progression_summary[exercise].last_notes` (or full Notes via `--include-rows`). If a note exists, treat the row as user-acknowledged context, not as an error. Acknowledge the context in the bullet rather than calling it a logging error. |
| Calling a deload on TSB alone when strength HR is unavailable | TSB -10.7 from two big hikes triggers a "fatigued" prescription even though strength load is invisible to TSB | When `capabilities.per_workout_hr_strength` is False, CTL/ATL/TSB are computed only from cardio TRIMPs — strength load is invisible. Don't treat a negative TSB as a unilateral deload trigger; cross-check with `recovery.score` and prefer recovery_score as the primary fatigue signal on these trackers. |
| Citing `non_interval_minutes` as Zone-2 minutes | Cardio check section reports `cardio_last_28d.non_interval_minutes` (which is just "cardio time that wasn't intervals") as if it were a real Z2 measurement — a 3h Z1 hike inflates the number | Read `cardio_hr_zones_28d.z2` for true Zone-2 minutes (HRR-based). Use `cardio_last_28d.non_interval_minutes` only as a fallback when `cardio_hr_zones_28d` is empty (no avg_hr on cardio sessions). |
| Skipping `swim_trajectory_callout` when `swim_summary` is present | The renderer surfaces the swim card with structured 14d trend data, but no coach commentary: the user reads numbers without judgment | Gate on `swim_summary` key presence. When present, author `cards.swim_trajectory_callout` per the card list in SKILL.md (verdict + 1 driver + 1 actionable focus). |
| Skipping `nutrition_phase_callout` when `nutrition_phase` is present | The dashboard shows the bulk/cut phase + status pill but no judgment; the binding `coach_action_hint` token reads as ungrounded | Gate on `nutrition_phase` key presence. When present, author `cards.nutrition_phase_callout` per the card list in SKILL.md. For `current.phase_type == "bulk"`, read `references/bulking-science.md` first. |
| Drafting `workout.md` before `coach_reads.json` is saved | The workout plan ends up paraphrasing the assessment in parallel instead of building on top of it; the two artifacts can drift | Hard checkpoint: write coach_reads.json to disk FIRST, then re-read it before drafting workout.md. The Pipeline (5 steps) section enforces this, and `check_plan.py` refuses the plan (exit 2) when `coach_reads.json` is not strictly older on disk than `workout.md`. |
| Skipping the `sleep` card when `sleep_summary` is present | Fully-populated sleep architecture gets zero coach output | Gate on `sleep_summary` key presence and author `cards.sleep` (and `trajectory_sleep`) per the card list in SKILL.md. Skip cleanly only when the key is absent (no nights in 28 days). |
| Skipping `recovery_practices` when `thermal_summary` or `light_therapy_summary` is present | The user logged sauna / cold / light sessions but the coach silently ignores them. Adherence and the HSP-threshold call are exactly the actionable bits. | Gate on the key's presence and author `cards.recovery_practices` per the card list in SKILL.md. Skip cleanly only when both keys are absent. |
| Inventing wavelength efficacy claims from light-therapy data | "660nm boosts mitochondrial ATP — push more red-light sessions." Source-honesty fails: the user's tracker only stores whether they did it and roughly how long; it has no individual response data. | Stay in protocol-adherence language: did the session happen, at roughly what duration. Don't extrapolate dose-response from N=user's own log. The reference for wavelength claims is the scientific literature, not the JSON. |
| Treating a context-change row as a real strength regression | Cable Lateral Raise drops from 15kg to 7kg after a gym change; coach flags the lift as "going backwards" with a -32kg/4w slope, even though the user's Notes say "new gym, different cable weights" | Read `estimated_1rm[exercise].context_change_excluded` and `progression_summary[exercise].last_notes`. When `context_change_excluded ≥ 1`, write "Slope reset by gym/equipment change; trend resumes once 3+ sessions logged on the new equipment" instead of calling stall or regression. |
| Writing a multi-set hold or carry as one token | `Plank: 45s hold` for a three-set plank. The validator counts it as ONE set, so the session silently delivers a third of the dose and can trip a false "under-allocated core" error. | One format for every unit: `Plank: 45s /// 45s /// 45s`, `Suitcase Carry: 24kgx30m /// 24kgx30m /// 24kgx30m`. Seconds, `MM:SS` and metres all count as set tokens, with a 10-second and 10-metre floor. |
| Prescribing an exercise that is not in the catalog | `Band Pull-Apart` was prescribed 9 times and is deliberately absent from `exercises-database.md` (no band equipment). The render gate rejects the name and the sets count as zero volume. | The catalog is the equipment list. Check `shared/exercises-database.md` before writing a name. `Hip Circle Walk` is in it and is legal; a plausible-sounding movement that is not in it is not prescribable. |
| Copying the equipment tag into the bullet | `Hip Circle Walk [Band]` or `Suitcase Carry [DB]` written as the exercise name. The bracket is catalog metadata, not part of the name, so the gate reports "not in the canonical exercise catalog" and the render exits 2. | Strip the tag. The bullet carries the bare canonical name: `Hip Circle Walk`, `Suitcase Carry`. |
| Re-prescribing a benched exercise, or benching a route-blocked one | A movement skipped in every session it was prescribed into comes back unchanged, or the coach quietly drops the only anti-rotation movement it has. | Read `adherence.benched` (never re-prescribe) and `adherence.bench_blocked` (keep prescribing, but ask for a substitute). Ask `bench_prompt.question` once and persist the answer with `adherence bench-record`, or the same question returns every run. |
| Quoting one adherence completion rate | `completion_rate` alone reads as truancy; `tested_completion_rate` alone hides missed sessions entirely. They move in opposite directions. | Quote both, or neither. The gap between them is attendance; `tested_completion_rate` alone is within-session truncation. `missed_sessions` is separate and is not evidence that the user rejects the movements inside those sessions. |
| Not disclosing that mid-block repetition is deliberate | Selection is deliberately held stable inside a 4-6 week block and only the load moves, but nothing says so, so a week that looks like last week reads as the coach being lazy. The user's original complaint was "every plan is the same plan". | Write the `block_position` card every week from `block.age_weeks` / `max_weeks` / `weeks_to_boundary`: where they are, that selection holds by design, when the next rotation lands. Then name the concrete dose changes from `next_dose` (which lifts took weight, which took reps, which held and why) so it does not read as "nothing changed". |
| Rotating on equipment flavour | Cable Lateral Raise becomes Dumbbell Lateral Raise at a block boundary and the plan is called new | Rotation means changing movement pattern or region tag. `blocks.rotation_diff_errors` rejects an equipment-only swap. Anchors change only on a 3-session stall, injury, or three blocks of age. |
| Skipping the block write at a boundary | `block.boundary_due` fires, a new block is authored, and nothing is persisted, so generation N+1 again has nothing to differ from | Run `python3 -m workout_coach.lib.blocks write --person <Name> --from-plan <date>` after writing the plan. An underived block is not a record. |
| Reporting an unresolved bodyweight trend as a direction | "Down 0.37 kg/wk" over a stretch whose honest fit was +0.07 ± 0.25; the coach reported leaning out across a stretch the user actually gained weight over | Read `bodyweight_trend.state` first. `unresolved` is an answer: say the direction is not resolved and give the reason. Never quote `point_kg_per_week` — or waist's `point_cm_per_4w` — as if it were the rate. Both sit beside `state` in their block and neither is gated on anything: the state check is the reader's job. |
| Reading body composition off the scale when waist is empty | "Up 1.2kg — the bulk is working" with no `waist_latest` on file. Bodyweight alone cannot separate recomposition from fat gain, so the claim is a coin flip dressed as a finding. | Waist is the leanness channel. With `waist_trend_cm_per_4w` resolved, read the two together. With one reading, call it a baseline and claim no direction. With `waist_latest` null, say the channel is empty out loud instead of omitting it — a silent omission reads as "nothing to report". |
| Trusting recovery `confidence: high` on under-sampled signals | A high-weight signal with `n_recent: 1` (one HR-Recovery reading) inflates confidence to "high" even though the score is hanging on one data point | Confidence is gated on per-signal sample sufficiency in `health_recovery.py`. When the JSON shows `confidence: medium` or `low` after a thin recent week, soften any rule that relies on the score band — and cite the under-sampled driver by name. |
